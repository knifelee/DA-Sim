# ScienceBenchmark: A Complex Real-World Benchmark for Evaluating NL-to-SQL Systems

## 1. Paper Information

- **Title:** ScienceBenchmark: A Complex Real-World Benchmark for Evaluating Natural Language to SQL Systems
- **Authors:** Yi Zhang, Jan Deriu, George Katsogiannis-Meimarakis, Catherine Kosten, Georgia Koutrika, Kurt Stockinger
- **Venue:** Proceedings of the VLDB Endowment (PVLDB), 2024
- **arXiv:** https://arxiv.org/abs/2306.04743
- **Data repo:** https://github.com/ckosten/sciencebenchmark_dataset
- **Benchmark Website:** https://sciencebenchmark.cloudlab.zhaw.ch/

---

## 2. Overview

ScienceBenchmark targets a gap that Spider and BIRD do not cover well: **complex, highly domain-specific scientific databases with little to no naturally occurring training data**. Rather than sampling many shallow databases across many domains, it goes deep on three real, large, high-column-count scientific databases, each with expert-written and expert-verified NL/SQL pairs.

Each of ScienceBenchmark's three databases is individually much larger and deeper than a typical Spider or BIRD database, even though there are only three of them in total.

---

## 3. Dataset Scope

This project uses ScienceBenchmark's **dev split only** — the manually written, held-out evaluation set — for the same reason `bird-dev/` uses only BIRD's dev split: to provide a focused evaluation setting for testing NL2SQL algorithms without requiring a training process. ScienceBenchmark's `seed` (100 examples/domain, hand-written) and `synth` (LLM-generated from seed templates, thousands of examples/domain) splits exist as training resources but are not included here.

| Layer | Description |
|---|---|
| Full ScienceBenchmark | 3 domains, `seed`/`synth`/`dev` splits, 5,031 total NL/SQL pairs |
| Dev split (this repository) | 3 domains, 299 combined dev-set tasks |

## 4. Dataset Statistics

**3 databases, one per domain** — unlike BIRD's many-databases-per-domain structure, each ScienceBenchmark domain maps to exactly one database:

| Domain | Database | Tables | Columns (paper) | Columns (this repo's actual restored DB) | Dev examples |
|---|---|---|---|---|---|
| Research policy making | `cordis` | 19 | 82 | 91 | 100 |
| Astrophysics | `sdss` | 6 | 61 | 61 | 100 |
| Cancer research | `oncomx` | 25 | 106 | 111 | 99 |
| **Total** | | | | | **299** |

For comparison, Spider averages 3.5 tables/database and BIRD averages 7.5 tables/database — each ScienceBenchmark domain's single database is considerably deeper than a typical database in either of those benchmarks.

**Column count note:** `tables.json` in this repository was generated by directly introspecting the restored databases (rather than reusing the upstream Spider-format `tables.json`), to guarantee it exactly matches the real `.sqlite` files and `database_description/` CSVs. This surfaces a few more columns per database than the paper's published counts for `cordis` and `oncomx` — e.g. `cordis.project_members` has real `region_code`/`region_name` columns, and `cordis.institutions` has a `document_vectors` column, that the original curated release omitted. `document_vectors` in particular is a PostgreSQL full-text-search tsvector artifact (e.g. `'aldo':6 'bari':5 ...`), not semantic data — it is retained rather than deleted, since this project prioritizes the `tables.json`/`database_description`/`.sqlite` triple being internally consistent over exactly reproducing the paper's curated column list, but it is not a meaningful column for NL2SQL question answering and can be safely ignored.

**Note:** OncoMX has 99 dev examples, not the 100 the original paper states — this is a genuine discrepancy in the publicly released `dev.json`, not an error introduced by this repository (confirmed directly against the downloaded source data).

## 5. Key Features

### 5.1 Deep, Real Scientific Schemas

CORDIS (EU research-funding records), SDSS (astrophysical object catalog), and OncoMX (cancer biomarker/gene-expression data) are each real, actively used scientific databases — not toy schemas built for the benchmark.

### 5.2 Expert-Written Questions

Unlike BIRD's crowd-sourced annotations, ScienceBenchmark's `seed` and `dev` splits were written and verified by domain experts together with SQL experts, targeting realistic questions a scientist in that field would actually ask.

### 5.3 No BIRD-Style Value-Level Descriptions

ScienceBenchmark's public release does not ship BIRD-style `database_description/` CSVs with human-authored column and value semantics. The `database_description/*.csv` files in this repository are therefore populated with column names and declared SQL types only (via schema introspection); `column_description` and `value_description` are intentionally left blank rather than fabricated.

### 5.4 Databases Distributed as PostgreSQL, Converted to SQLite Here

ScienceBenchmark's official databases are distributed as PostgreSQL dumps (schemas `unics_cordis`, `lite`, `oncomx_v1_0_25`), not SQLite. For consistency with this project's format, they were restored to a local PostgreSQL instance and converted to SQLite (via direct schema/data introspection, preserving primary and foreign keys) to produce `databases/<domain>/<domain>.sqlite`. Minor cross-engine semantic differences between PostgreSQL and SQLite (e.g., type coercion in comparisons) mean a small number of gold queries may return slightly different row counts between engines — see the execution-accuracy note below.

## 6. Gold-Query Execution Validation

Every gold query in `gold.sql` was executed directly against this repository's converted SQLite databases (not just checked for valid syntax):

| Domain | Dev queries | Execute, non-empty | Errors | Empty |
|---|---|---|---|---|
| `cordis` | 100 | 93 | 0 | 7 |
| `sdss` | 100 | 100 | 0 | 0 |
| `oncomx` | 99 | 90 | 2 | 7 |

**Two confirmed authoring bugs in OncoMX's gold SQL** (question_id 293 and 298 in `nl_queries.json`), both alias-misuse bugs where a query joins a table with an alias but a later clause references the unaliased table/column name:
- Q293 ("genes related to biomarkers of prostate cancer"): joins `biomarker_fda AS bio_fda`, then references the unaliased `biomarker_fda` name.
- Q298 ("biomarkers and the species they're expressed in"): joins `species AS s`, but `SELECT` references the unaliased `species.species` instead of `s.species`.

Both referenced tables genuinely exist in the schema, confirming these are authoring bugs in the released gold standard, not schema drift introduced by this repository. The empty-but-error-free results (7 for CORDIS, 7 for OncoMX) were not individually diagnosed — they may be legitimate zero-row answers or further gold-query drift.

## 7. Relevance to Ambiguity-Aware NL2SQL

| Ambiguity Layer | Description |
|---|---|
| Domain-terminology ambiguity | Scientific column and table names (e.g., biomarker/gene/tissue relationships in OncoMX, astronomical object classifications in SDSS) require domain expertise to interpret correctly, more so than typical business-data benchmarks. |
| Missing semantic layer | With no `database_description`-style annotations, resolving what a column means relies entirely on naming and schema structure. |
| Deep-schema join ambiguity | With up to 25 tables and 106 columns in a single database, correctly identifying the join path connecting a question's entities is substantially harder than in a typical Spider/BIRD database. |
| Gold-answer reliability | The two confirmed OncoMX alias bugs are a concrete reminder that "ground truth" SQL can itself be wrong — directly relevant to evaluating systems that must reconcile generated SQL against a possibly-flawed reference. |
